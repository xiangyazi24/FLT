The same file also has:

That last theorem is useful for quotient-scalar changes, but it is not a replacement for residue-field conversion when comparing an F₂-length with a local-ring length.

### Mathlib/Algebra/Module/ZMod.lean

At the same pin:

```javascript
theorem ZMod.map_smul
    (f : F) (c : ZMod n) (x : M) :
    f (c • x) = c • f x
```

for any additive hom-class map between ZMod n-modules.

Also:

```javascript
def AddMonoidHom.toZModLinearMap
    (f : M →+ M₁) :
    M →ₗ[ZMod n] M₁
```

So an AddEquiv, and hence a RingEquiv through RingEquiv.toAddEquiv, is automatically ZMod n-linear. There is no direct pinned theorem named RingEquiv.length_eq or AddEquiv.length_eq; the correct route is:

```plain text
RingEquiv
  -> RingEquiv.toAddEquiv
  -> reinterpret as LinearEquiv over ZMod 2
  -> LinearEquiv.length_eq
```

LinearEquiv.ofBijective is also present at the pin if one prefers to construct a linear map with AddMonoidHom.toZModLinearMap and then upgrade it using bijectivity.

### Mathlib/RingTheory/LocalRing/Length.lean

The pinned residue-field conversion theorem is exactly:

```javascript
theorem IsLocalRing.length_restrictScalars
    (A B M : Type*) ... :
    Module.length A M =
      Module.length B M *
        Module.length (ResidueField A) (ResidueField B)
```

under the local-ring / local-hom / scalar-tower hypotheses.

For an F₂-rational point, the last factor must be proved to be 1. Only then may one replace local-ring length by F₂-module length.

## 2. Tiny helper: turn the existing ring equivalence into an F₂-linear equivalence

This is the least fragile construction because it uses the pinned ZMod.map_smul theorem directly:

```javascript
private def zmodLinearEquivOfAddEquiv
    {n : ℕ} {M N : Type*}
    [AddCommGroup M] [AddCommGroup N]
    [Module (ZMod n) M] [Module (ZMod n) N]
    (e : M ≃+ N) :
    M ≃ₗ[ZMod n] N :=
  { e with
    map_smul' := fun c x => ZMod.map_smul e c x }

private def zmodLinearEquivOfRingEquiv
    {n : ℕ} {A B : Type*}
    [Ring A] [Ring B]
    [Module (ZMod n) A] [Module (ZMod n) B]
    (e : A ≃+* B) :
    A ≃ₗ[ZMod n] B :=
  zmodLinearEquivOfAddEquiv e.toAddEquiv
```

If the file already has a local helper of this kind, reuse it rather than adding another copy.

An equivalent construction using only named constructors is:

```javascript
let f : A →ₗ[ZMod n] B :=
  AddMonoidHom.toZModLinearMap n e.toAddEquiv.toAddMonoidHom
let E : A ≃ₗ[ZMod n] B :=
  LinearEquiv.ofBijective f (by
    simpa [f] using e.bijective)
```

The structure-literal version above is shorter and avoids a coercion/bijectivity elaboration detour.

      (Localization.Away wChartDenominator ⧸
        Ideal.map
          (algebraMap BinaryAffinePlane
            (Localization.Away wChartDenominator))

            {wChartQuadricPolynomial, wChartCubicPolynomial}))
        ≃ₗ[ZMod 2] DoubleArtin :=
    zmodLinearEquivOfRingEquiv doubleLocalizedChartQuotientEquiv

A slightly more explicit final two lines are:

```javascript
calc
  Module.length (ZMod 2) DoubleArtin
      = Module.finrank (ZMod 2) DoubleArtin :=
    Module.length_eq_finrank (ZMod 2) DoubleArtin
  _ = 2 := by simp [doubleArtin_finrank]
```

The important implementation advantage is that Module.length_eq_finrank is invoked on DoubleArtin, not on the localized quotient. Therefore the proof does not require Lean to infer a separate [Module.Finite (ZMod 2) QW] instance for the chart quotient.

## 5. What these theorems prove — and what they do not

These two results are:

```plain text
ℓ_{F₂}(QW) = 2
ℓ_{F₂}(QYZ) = 3
```

Since ZMod 2 is a field, Module.length_eq_finrank identifies these with the F₂ vector-space dimensions.

They are not yet the local intersection multiplicities

```plain text
ℓ_{O_{C,W}}(O_{C,W}/(s_W))
ℓ_{O_{C,YZ}}(O_{C,YZ}/(s_YZ)).
```

In particular, do not write or justify

```javascript
Module.length (Localization.Away wChartDenominator) QW = 2
```

merely from doubleArtin_finrank.

There are two independent reasons:

1. Localization.Away wChartDenominator is a principal-open/chart ring, not automatically the local ring at W.

1. Even after passing to the stalk/local ring, Module.length R M is not definitionally or generally equal to Module.length (ZMod 2) M; the residue-field factor must be accounted for.

The numeral 2 itself is not a type problem — in a Module.length theorem it is an ℕ∞ numeral. The problem is the mathematical scalar ring, not the numeral coercion.

After that, the missing scalar comparison is residue-field degree one. The exact reusable lemma I would add is:

```javascript
theorem localLength_eq_f2Length_of_residue_length_one
    {R M : Type*}
    [CommRing R] [IsLocalRing R]
    [Algebra (ZMod 2) R]
    [IsLocalHom (algebraMap (ZMod 2) R)]
    [AddCommGroup M]
    [Module (ZMod 2) M]
    [Module R M]
    [IsScalarTower (ZMod 2) R M]
    (hres :
      Module.length
        (ResidueField (ZMod 2))
        (ResidueField R) = 1) :
    Module.length R M = Module.length (ZMod 2) M := by
  rw [IsLocalRing.length_restrictScalars (ZMod 2) R M,
    hres, mul_one]
```

This is exactly the missing logical bridge. At W and YZ, prove hres from the fact that the point is F₂-rational / its residue field is F₂, then apply the lemma to the stalk quotient. The chart/stalk quotient ring equivalence transports the F₂-length by the same zmodLinearEquivOfRingEquiv + LinearEquiv.length_eq mechanism used above.
