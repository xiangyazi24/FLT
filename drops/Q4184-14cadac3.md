# `flt1 --help`

`flt1` is a natural-language assistant for mathematical and Lean-engineering work around the FLT repository. It does not require a rigid command syntax: describe the goal in ordinary language, include the relevant source or error, and specify the form of the result you need.

```text
USAGE
  flt1 <request>
  flt1 --help

TYPICAL REQUESTS
  Explain a definition, theorem, proof, or file.
  Find the relevant Mathlib or repository API.
  Design a formalization strategy.
  Draft or repair Lean 4 code.
  Diagnose an elaboration, typeclass, simplifier, or build error.
  Review a proposed proof or patch for correctness and maintainability.
  Translate an informal mathematical argument into kernel-checkable lemmas.
  Produce a focused GitHub-ready answer, patch, review, or documentation note.
```

## Best request format

The most useful prompt supplies as many of these fields as are available:

```text
Repository/ref: owner/repository, branch, tag, or commit SHA
Files:          exact paths and, when useful, line ranges
Goal:           theorem statement or desired behavior
Context:        imports, namespace, variables, local notation, hypotheses
Current code:   smallest relevant Lean fragment
Failure:        complete error message or failing goal state
Constraints:    allowed imports, forbidden axioms, style/API requirements
Output:         explanation, proof plan, Lean code, patch, review, or memo
Verification:   whether a checked build is required or a proposed draft is enough
Delivery:       chat, GitHub branch/path, PR comment, or another explicit target
```

A minimal but strong Lean request looks like this:

```text
On `scratch`, repair `path/File.lean` without adding imports.
Here is the theorem, current proof, and full compiler error.
Return the smallest replacement proof and explain any non-obvious API choice.
```

## What `flt1` can do

### Repository orientation

`flt1` can inspect named branches, commits, files, pull requests, issues, and review discussions available through the connected repository tools. It can trace definitions and theorem usage, compare refs, identify likely extension points, and summarize the local architecture before proposing changes.

### Lean proof engineering

It can help with:

- theorem and definition discovery;
- namespace, coercion, and notation problems;
- implicit arguments and typeclass inference;
- rewriting, extensionality, induction, and algebraic normalization;
- structures, subtypes, bundled morphisms, and universe issues;
- adapting proofs to the exact repository API;
- splitting a large mathematical goal into reusable intermediate lemmas;
- replacing brittle automation with maintainable proofs.

### Mathematical review

It can check an informal argument for missing hypotheses, normalization mistakes, sign errors, invalid converse steps, exceptional cases, and mismatches between a mathematical construction and its Lean representation. When a complete proof is not yet justified, it should isolate the exact unresolved lemma rather than hide it behind confident prose.

### Code and patch review

It can review a diff for correctness, scope, API compatibility, proof robustness, unnecessary imports, duplicated lemmas, naming, documentation, and likely CI failures. It can also turn selected findings into a concrete replacement snippet or repository write when explicitly authorized.

### Documentation and planning

It can produce theorem inventories, dependency maps, implementation plans, design notes, experiment reports, and handoff documents. A useful plan names exact definitions and proof obligations instead of merely restating the desired theorem.

## Output modes

Ask for one or combine several:

```text
EXPLAIN       Plain-language explanation with exact source references.
PLAN          Ordered formalization plan with dependencies and risk points.
LEAN          Complete Lean snippet with imports and namespace context.
PATCH         Minimal file-level replacement or diff-oriented instructions.
REVIEW        Prioritized findings, each tied to evidence and a remedy.
API SEARCH    Candidate declarations, expected types, and how they compose.
CHECKLIST     Concrete next steps suitable for implementation or review.
DELIVERY      Write the complete result to an explicitly named GitHub/Notion target.
```

## Verification labels

A response should distinguish these states clearly:

```text
VERIFIED      Checked against the requested repository/ref with an available build
              or authoritative tool result.
SOURCE-CHECKED
              Declarations and file context were inspected, but no full build ran.
PROPOSED      Reasoned draft that still needs elaboration or compilation.
BLOCKED       A specific missing file, error log, dependency, permission, or API fact
              prevents responsible verification.
```

No proof should be described as compiling merely because it looks plausible. When no Lean build is run, the result should say so and identify the most likely elaboration-sensitive lines.

## Request examples

```text
Find the declaration used to base-change a Weierstrass curve to `PowerSeries K`,
then give the smallest proof that the formal point satisfies the projective equation.
```

```text
Review PR 123. Focus on mathematical correctness and unresolved inline comments.
Do not change files; return prioritized findings with exact paths.
```

```text
This `simp` proof broke after an API change. Use only the imports already present,
avoid `aesop`, and return a proof that is stable under harmless simp-set changes.
```

```text
Turn the following descent argument into a Lean roadmap. Separate the algebraic
identities, local-solubility certificates, and the final global contradiction.
```

```text
Write the complete answer to `drops/QNNNN-token.md` on the `scratch` branch.
Make the required marker the first line and report the resulting commit SHA.
```

## Practical guidance

Provide the full error rather than only its last line. Pin a branch or commit when reproducibility matters. Include surrounding definitions when local notation or instances affect the goal. State whether changing theorem statements, adding imports, using classical logic, or introducing helper lemmas is permitted.

For large goals, request a staged answer: first an API inventory, then a proof skeleton, then the smallest verified patch. For delicate mathematics, ask for both the mathematical invariant and the corresponding Lean statement; this often exposes representation errors early.

## Write-safety behavior

Repository, issue, pull-request, calendar, mail, or document mutations should occur only when the request explicitly authorizes them and identifies the target. A write response should report what changed and return the resulting stable identifier, such as a commit SHA, issue number, page ID, or event ID.

## Scope boundary

`flt1` can reason from supplied material and inspect connected sources it is authorized to access. It cannot treat an unavailable private file, an unobserved compiler run, or an unspecified branch state as known. When information is missing, it should make the narrowest explicit assumption possible and keep proposed code clearly separated from verified code.
