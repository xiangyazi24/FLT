```lean

```

Then replace the axiom, preserving its existing name and type. In the most likely form, the change is:

```diff

+theorem no_order_18

-    ¬ HasRationalPointOfOrder E 18
+    ¬ HasRationalPointOfOrder E 18 := by
```

Equivalently, as complete Lean code:

```lean

    (E : WeierstrassCurve ℚ) [E.IsElliptic] :
```

If the imported theorem lives in another namespace, qualify that theorem with the namespace actually printed by Lean:


or whatever namespace the staging file declares. A filename does **not** automatically create a Lean namespace, so `CyclicExclusion18.no_rational_point_of_order_18` is valid only if the file explicitly contains `namespace CyclicExclusion18`.

If the two declarations have definitionally identical types, the absolute shortest adapter is:

```lean

```

The explicit version is preferable because it gives clearer elaboration errors if the old axiom and the proved theorem use slightly different wrappers for “has a rational point of order 18.”

### If the old axiom is pointwise rather than existential

The instruction “preserve the old header verbatim” matters. For example, if the old axiom is shaped like

```lean
axiom no_order_18
    (E : WeierstrassCurve ℚ) [E.IsElliptic]
    (P : E.toAffine.Point) (hP : addOrderOf P = 18) : False
```

while `no_rational_point_of_order_18` is stated as the negation of an existential, use the following adapter:

```lean
theorem no_order_18
    (E : WeierstrassCurve ℚ) [E.IsElliptic]
    (P : E.toAffine.Point) (hP : addOrderOf P = 18) : False := by
  exact no_rational_point_of_order_18 (E := E) ⟨P, hP⟩
```

Conversely, if both declarations already have the same proposition, the one-line `exact` above is sufficient.

## What happens to `#print axioms`

The dependency disappears **automatically** after the affected modules are rebuilt. There is no separate axiom-registration table and no explicit command to remove an axiom from a theorem.

`#print axioms declarationName` recursively follows the constants used by the declaration and reports the primitive axioms in that dependency closure. After the replacement,

```text
mazur_cyclic_order_bound_assembled
  → no_order_18                    -- now a theorem
  → no_rational_point_of_order_18  -- theorem
  → no_obstruction18               -- theorem
  → no_five_descent_solution       -- theorem
  → N18 proof chain
```

so the old `no_order_18` axiom is no longer in the closure and will no longer be printed.

Nothing additional is required beyond recompilation. However, “0 `sorry` in `N18GoodModelAssembly.lean`” is not by itself a complete transitive audit: an imported theorem can still depend on an axiom. Check the chain from bottom to top:

```lean
#print axioms no_five_descent_solution
#print axioms no_obstruction18
#print axioms no_rational_point_of_order_18
#print axioms no_order_18
#print axioms mazur_cyclic_order_bound_assembled
```

Expected harmless foundational entries can include such constants as

```text
propext
Classical.choice
Quot.sound
```

The entries that should disappear are the project-specific `no_order_18` axiom and any `sorryAx` arising from the N18 chain.
