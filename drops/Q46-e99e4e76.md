# N18 port: likely Lean 4 failure modes and a concrete triage plan

## Executive assessment

The line count itself is not the main risk. Lean elaborates a module declaration by declaration, so a 3100-line file can be routine while one 20-line `simp`/`ring_nf`/typeclass declaration can dominate the entire build.

For this port, I would rank the likely failure modes as follows:

1. **Lean/mathlib/package-version drift between staging and working repositories.**
2. **`scratch.KeystoneEDS` not being a clean-build dependency, or having changed API/attributes.**
3. **A hidden transitive import lost when `CyclicExclusion18` was removed, or a remaining indirect import cycle.**
4. **Instance or simp-set drift caused by the changed import graph.**
5. **A stale `.olean` making the incremental build look healthier than a clean build.**
6. **One unbounded expensive declaration in `N18GoodModelAssembly.lean`.**
7. **Ordinary namespace/type-signature drift for cross-file constants such as `normReal`.**

The connector-visible repository currently has a particularly important version split:

```text
scratch:
  Lean     v4.31.0-rc2
  mathlib  96fd0fff3b8837985ae21dd02e712cb5df72ec05

main:
  Lean     v4.32.0-rc1
  mathlib  c0cbc05a6f61999c6e6e8afdcbbe0b3daff95a27
```

If the staging and working repositories correspond even approximately to those two environments, **version drift is the first thing to check**, before debugging any mathematical proof.

# 1. `set_option maxHeartbeats 0`

## What it means

```lean
set_option maxHeartbeats 0
```

means **no Lean heartbeat limit** for declarations in the scope of that option. It does not mean:

- no operating-system timeout;
- no GitHub Actions or CI job timeout;
- no memory limit;
- no recursion-depth limit;
- no stack overflow;
- no native-code compiler failure;
- no process kill by the scheduler.

It removes Lean's main protection against a tactic or elaboration search running for an unexpectedly long time.

## Effect of your hardware

Your 32 cores and 251 GB RAM are excellent for building many independent modules in parallel. They do much less for one large declaration:

- Lake can compile independent modules concurrently.
- A single Lean module is elaborated mostly sequentially.
- A single expensive theorem usually occupies roughly one core.
- Extra RAM prevents many ordinary OOM failures, but it does not make a divergent `simp`, `aesop`, or typeclass search terminate.

Thus it is quite possible to see one `lean` process at about one-core utilization for a long time even on a 32-core machine.

## Could it time out on another machine?

Yes. The same proof may elaborate successfully on your workstation but exceed an external wall-clock limit on CI or a slower machine. Heartbeats are intended to be more stable than wall-clock time, but changing Lean or mathlib versions can alter the number and cost of elaboration steps substantially.

A declaration with unlimited heartbeats is especially dangerous after a port because a formerly fast search may have become exponentially slower while still being logically valid.

## Recommended treatment

Do not immediately remove the option if the staging proof needed it. First get a clean successful build. Once the port works:

1. identify the expensive declarations;
2. scope `maxHeartbeats 0` only around those declarations;
3. preferably replace `0` by a measured finite budget with generous margin.

For example:

```lean
set_option maxHeartbeats 8_000_000 in
 theorem expensive_assembly_lemma : ... := by
  ...
```

The exact finite number should come from profiling, not from guessing.

To profile the large source file temporarily, use either:

```lean
set_option trace.profiler true
```

near the top, or the command-line option supported by the pinned Lean:

```bash
lake env lean -Dtrace.profiler=true path/to/N18GoodModelAssembly.lean
```

Also distinguish heartbeat failure from recursion failure. This error:

```text
maximum recursion depth has been reached
```

is controlled by `maxRecDepth`, not by `maxHeartbeats`.

## Performance interpretation

During a slow clean build:

- **one core busy, stable RSS:** probably one legitimately expensive theorem;
- **one core busy, rapidly growing RSS:** likely term explosion, simplifier explosion, or unification blow-up;
- **many Lean processes:** ordinary parallel module compilation;
- **little CPU use:** waiting for a package lock, compiler, download, or external process;
- **works with one Lake worker but fails with 32:** memory/IO contention rather than proof invalidity.

For diagnosis, first compile the suspect module with one Lake worker. Parallelism is useful only after the individual modules are known to be healthy.

# 2. `scratch.KeystoneEDS` is the highest-risk dependency

This import is a stronger warning sign than the size of the assembly file:

```lean
import scratch.KeystoneEDS
```

## Clean-build/module-discovery risk

The connector-visible `lakefile.toml` declares the production library with:

```toml
[[lean_lib]]
name = "FLT"
globs = ["FLT", "FermatsLastTheorem"]
```

A root module named `scratch.KeystoneEDS` is outside those globs unless there is another `lean_lib` declaration for `scratch`.

That creates the classic failure pattern:

```text
incremental local build succeeds
fresh clone or `lake clean` build fails
```

because a manually produced or staging-produced

```text
.lake/build/lib/lean/scratch/KeystoneEDS.olean
```

may be present locally even though Lake has no reproducible source rule for it.

Typical errors are:

```text
unknown module prefix 'scratch'
```

or

```text
object file .../scratch/KeystoneEDS.olean does not exist
```

## Case-sensitivity risk

The import requires a matching module path, normally:

```text
scratch/KeystoneEDS.lean
```

A capitalization discrepancy such as `Scratch/KeystoneEDS.lean` can be masked on a case-insensitive development filesystem and fail on Linux CI.

## API drift risk

Even if the module is found, compare its exact contents between repositories. Changes that can break a previously sorry-free client include:

- theorem renamed or moved to another namespace;
- argument order or implicit parameters changed;
- a `def` changed to an `abbrev`, `opaque`, or theorem;
- a theorem becoming less definitionally reducible;
- a local instance becoming global, or vice versa;
- instance priority changes;
- new or removed `[simp]` attributes;
- changed coercion targets;
- different imported notation scopes;
- a theorem retaining its name but changing from equality to an iff or vice versa.

The most subtle case is when every explicitly named theorem still exists but broad tactics behave differently because `KeystoneEDS` changed the global simp set or instance environment.

## What to do

For a production Mazur proof, I would not leave the dependency under `scratch`.

Preferred repair:

```text
scratch/KeystoneEDS.lean
  -> FLT/Mazur/N18/KeystoneEDS.lean

import scratch.KeystoneEDS
  -> import FLT.Mazur.N18.KeystoneEDS
```

Then expose only the small stable API actually consumed by `N18PackageII`.

At minimum, verify the exact source hash from staging and working copies. Conceptually:

```bash
git hash-object path/to/staging/scratch/KeystoneEDS.lean
git hash-object path/to/working/scratch/KeystoneEDS.lean
```

The two hashes should match unless you have intentionally ported the client to a new Keystone API.

## Trust audit

“Zero `sorry` in the four ported files” does not by itself imply that the final theorem has no project-specific axioms. An imported theorem can depend on an axiom.

After the clean build, run the equivalent of:

```lean
#print axioms MazurProof.CyclicExclusion18.no_rational_point_of_order_18
#print axioms MazurProof.no_order_18
```

Standard foundational items such as `propext`, `Classical.choice`, and `Quot.sound` may appear. What should not appear is an old project axiom such as `no_order_18`, a Keystone placeholder, or another N18 assumption.

This check is especially important because the repository currently has:

```toml
warn.sorry = false
```

so ordinary build output is not a sufficient trust audit.

# 3. Cross-file names such as `MazurProof.RationalPointsN18Descent.normReal`

## Fully qualified names are normally robust

A reference such as

```lean
MazurProof.RationalPointsN18Descent.normReal
```

is not normally affected by `open` declarations or by another namespace being opened. If the exact declaration is imported with the same type, fully qualified lookup is the safest form.

Thus pure namespace ambiguity is not the most likely problem.

## What can still differ

The following can still fail between repositories:

1. The defining module is no longer imported.
2. The declaration moved to a different namespace.
3. Its type changed, even if its name did not.
4. Its implicit arguments changed.
5. A type synonym used by it changed reducibility.
6. A required instance is no longer in scope.
7. The working repository already contains a declaration with the same full name.
8. The file was copied under different enclosing `namespace`/`section` nesting.
9. The symbol was previously visible only through the removed transitive import.

## Removing an apparently unused import

Removing

```lean
import ...CyclicExclusion18
```

from Assembly was likely the right architectural move, but “Assembly does not mention a declaration defined in that file” is not enough to prove the import was unnecessary.

The import may have supplied transitively:

- `RationalPointsN18Descent.normReal` itself;
- a valuation module;
- notation;
- a scoped notation namespace;
- instances;
- simp lemmas;
- tactics or elaborator extensions.

Lean imports are transitive, so source code can accidentally rely on an import several layers away. A clean build of Assembly with its new minimal import list is the real test.

The durable repair is to add direct imports for the modules defining every external declaration used by Assembly. Do not restore the high-level cyclic-exclusion import merely to recover low-level symbols.

A useful temporary smoke check immediately below the imports is:

```lean
#check MazurProof.RationalPointsN18Descent.normReal
#check MazurProof.RationalPointsN18Descent.someOtherRequiredConstant
```

Delete or move these checks to a test file after the import list is stable.

## Instance and simp pollution after moving the import

Adding `CyclicExclusion18` to `CyclicOrderAssembly.lean` can change more than name visibility. Imports add global instances and attributes to the environment. Consequently a proof in `CyclicOrderAssembly` may now:

- find two competing instances;
- choose a different coercion path;
- make `simp` loop or become much slower;
- have `aesop` explore many more rules;
- trigger `maxSynthPendingDepth = 3` failures.

When a proof becomes unstable after an import change, inspect broad calls such as:

```lean
simp
simp_all
aesop
norm_num
infer_instance
```

In hot declarations, prefer explicit instances and `simp only [...]`.

# 4. Import-cycle risks after replacing the axiom

The intended dependency direction should be approximately:

```text
N18GoodModelValCoords
N18ReductionGood
N18PackageII
          \
           -> N18GoodModelAssembly
                    -> CyclicExclusion18
                            -> CyclicOrderAssembly
```

`CyclicOrderAssembly` should be the top layer. There must be no arrow from any lower layer back to it.

## The remaining hidden-cycle possibilities

Even after removing the direct `CyclicExclusion18` import from Assembly, a cycle can remain if, for example:

```text
CyclicOrderAssembly
  imports CyclicExclusion18

CyclicExclusion18
  imports SomeIntermediateFile

SomeIntermediateFile
  imports CyclicOrderAssembly
```

or if `CyclicExclusion18` itself previously imported `CyclicOrderAssembly` to obtain the old axiom.

Lean/Lake will report an import cycle, but the message may show module names far from the edit that caused it.

## Placement of the wrapper theorem

The wrapper

```lean
theorem no_order_18 :=
  CyclicExclusion18.no_rational_point_of_order_18
```

belongs in a module downstream of `CyclicExclusion18`. No module needed to prove `CyclicExclusion18.no_rational_point_of_order_18` may import that wrapper module.

Use the fully qualified theorem name in the proof. This avoids accidental self-reference or resolution to a compatibility alias with the same short name.

Prefer `exact` when the types are definitionally identical:

```lean
exact CyclicExclusion18.no_rational_point_of_order_18 E h
```

Use a narrow `simpa only [...] using ...` only if a small, understood wrapper difference remains. A broad `simpa` here can hide a type mismatch or introduce simplifier instability.

## Search for the old declaration

Before trusting the build, ensure there is not another declaration elsewhere:

```bash
rg -n 'axiom no_order_18|theorem no_order_18' FLT FermatsLastTheorem scratch
```

Two declarations with the same full namespace/name cause an immediate duplicate-declaration error. Two declarations in different namespaces can cause an unqualified reference to resolve differently than expected.

# 5. Common failure modes for a 3000-line Lean module

## 5.1 Stale `.olean` files

This is the most common reason a port appears to work incrementally and fails in CI.

A stale artifact can mask:

- a missing source file;
- a missing import;
- an import outside the library globs;
- an old axiom declaration;
- a theorem compiled against an old type;
- a different Lean binary.

A clean build is mandatory before declaring success.

## 5.2 Toolchain and mathlib drift

Compare all three, not just one:

```text
lean-toolchain
lakefile.toml or lakefile.lean
lake-manifest.json
```

Also inspect the checked-out dependency itself:

```bash
lean --version
git -C .lake/packages/mathlib rev-parse HEAD
```

Do not run `lake update` casually while diagnosing. It can move dependencies and create a second porting problem. First decide which exact staging revision is authoritative.

Typical version-drift errors include:

```text
unknown constant ...
invalid field notation
application type mismatch
failed to synthesize ...
function expected at ...
unsolved goals after simp
```

Valuation and completion APIs are especially sensitive to mathlib revisions, so `N18GoodModelValCoords` and `N18ReductionGood` are good early canaries.

## 5.3 Broad simplifier or typeclass behavior changes

The global environment grows throughout a large module. A `simp` near line 3000 sees every imported and previously declared simp lemma. A proof that was fast in staging may become slow after adding one imported file with many attributes.

Watch for:

- `simp` using an unintended new rewrite;
- simp loops;
- `simp_all` term explosion;
- `aesop` search explosion;
- ambiguous coercions;
- duplicate local/global instances;
- synthesis stuck at `maxSynthPendingDepth`.

The cure is usually local explicitness, not more heartbeats.

## 5.4 Huge proof terms

Tactics such as

```lean
ring
ring_nf
norm_num
native_decide
field_simp
linarith
nlinarith
```

can produce large proof terms or expensive normalization. The source may be short while kernel checking and `.olean` serialization are expensive.

For large polynomial identities:

- split identities into named lemmas;
- keep coefficient normalizations local;
- avoid repeatedly unfolding the same enormous definitions;
- use `change` or `show` to present a smaller normalized goal;
- consider a pre-proved certificate rather than asking `ring_nf` to rediscover it repeatedly.

## 5.5 `native_decide` and code generation

A staging file using `native_decide` can fail in a new environment because of:

- toolchain code-generation changes;
- a definition becoming `noncomputable`;
- missing compiler support;
- a changed finite type instance;
- very large generated native code.

An error from the native compiler is not fixed by `maxHeartbeats 0`.

## 5.6 Scope damage during copy/merge

Large copied files are vulnerable to a misplaced:

```lean
end
end SomeNamespace
section
noncomputable section
```

This can change the full names or inferred parameters of hundreds of later declarations.

Other scope-sensitive items include:

```lean
open scoped ...
local notation ...
local instance ...
attribute [local simp] ...
include ...
omit ...
```

A missing `noncomputable section` often first appears as a complaint far below the place where the scope was lost.

## 5.7 Duplicate declarations

If the working repository already had preliminary versions of the same lemmas, the port may fail with:

```text
'...' has already been declared
```

Do not rename one copy merely to make the build pass. Decide which implementation is authoritative and remove or turn the other into an explicit compatibility alias.

## 5.8 Filesystem/module-name mismatch

Check that each filename and import uses exactly matching capitalization. This matters particularly when moving from macOS to Linux.

Also verify that all four files are tracked by Git and lie under a configured library glob.

## 5.9 Warning policy and lint/test differences

A plain module build can succeed while CI later fails because of:

- declaration lint;
- unused arguments or style warnings treated as errors by a test driver;
- `#print axioms`/`checkdecls` checks;
- an umbrella import failure in `FLT.lean`;
- test modules importing the old axiom path.

After the focused build, run the same top-level target and test command used by CI.

# 7. Recommended clean-build protocol

Do this in a fixed order so the first failing layer is obvious.

## Step 1: freeze and compare versions

Record:

```bash
lean --version
git rev-parse HEAD
git -C .lake/packages/mathlib rev-parse HEAD
```

Compare staging and working copies of:

```text
lean-toolchain
lakefile.toml / lakefile.lean
lake-manifest.json
scratch/KeystoneEDS.lean
```

If these differ, decide whether to align the environment or truly port the code. Do not mix the two tasks.

## Step 2: inspect the import DAG

List only import lines first:

```bash
rg -n '^import ' \
  path/to/N18PackageII.lean \
  path/to/N18GoodModelValCoords.lean \
  path/to/N18GoodModelAssembly.lean \
  path/to/N18ReductionGood.lean \
  path/to/CyclicExclusion18.lean \
  path/to/CyclicOrderAssembly.lean
```

Confirm that dependency arrows flow upward and never return to `CyclicOrderAssembly`.

## Step 3: force a genuinely clean package build

Use `lake clean` or remove the working package's `.lake/build` directory. Do not rely on an `.olean` copied or generated in the staging repository.

If `scratch.KeystoneEDS` is outside the source map, this is the step that should expose it.

## Step 4: build leaf modules one at a time

Use one Lake worker for diagnosis and build approximately in this order, adjusted to the actual imports:

```text
N18GoodModelValCoords
N18ReductionGood
N18PackageII
N18GoodModelAssembly
CyclicExclusion18
CyclicOrderAssembly
```

For example, with the actual module names substituted:

```bash
time lake build -j 1 <N18GoodModelValCoords-module>
time lake build -j 1 <N18ReductionGood-module>
time lake build -j 1 <N18PackageII-module>
time lake build -j 1 <N18GoodModelAssembly-module>
time lake build -j 1 <CyclicExclusion18-module>
time lake build -j 1 <CyclicOrderAssembly-module>
```

Once all pass individually, run the full parallel build.

## Step 5: profile Assembly if it stalls

Temporarily run:

```bash
lake env lean -Dtrace.profiler=true path/to/N18GoodModelAssembly.lean
```

or add `set_option trace.profiler true` locally. Locate the declaration, not merely the file, responsible for the delay.

## Step 6: audit the final theorem

Create a tiny smoke-test module:

```lean
import <module-containing-CyclicOrderAssembly>

#check MazurProof.CyclicExclusion18.no_rational_point_of_order_18
#check MazurProof.no_order_18
#print axioms MazurProof.CyclicExclusion18.no_rational_point_of_order_18
#print axioms MazurProof.no_order_18
```

Use the actual namespaces from the repository.

## Step 7: reproduce from a fresh clone or CI-equivalent checkout

A successful incremental build is not the final test for this particular port because of the `scratch.KeystoneEDS` risk.

# 9. Direct answers to the four questions

## 1. Can `maxHeartbeats 0` cause timeout issues elsewhere?

Yes. It disables Lean's heartbeat cutoff but does not disable wall-clock or resource limits. Your hardware helps module-level parallelism and memory, but one declaration remains mostly single-threaded. Keep it for the first clean build if needed, then profile and localize it.

## 2. Can a changed `scratch.KeystoneEDS` break the port?

Absolutely. This is probably the single most likely source-level problem. It can fail because the module is not in the working library's clean build graph, because the source differs, or because attributes/instances changed even when theorem names did not. Move the needed API into a stable `FLT...` module and verify the final theorem's axioms.

## 3. Can namespace resolution for `normReal` differ?

A fully qualified name is stable against ordinary `open` differences. The real risks are missing imports, changed declaration types, altered namespace nesting, and changed instance/coercion environments. Removing `CyclicExclusion18` can expose a hidden transitive dependency, so add direct low-level imports rather than restoring the high-level cyclic import.

## 4. Are 3000-line files intrinsically problematic?

No. Large files mainly worsen rebuild granularity and make one pathological declaration harder to locate. The common real problems are stale artifacts, import drift, broad automation, instance ambiguity, huge proof terms, `native_decide` code generation, and unbounded heartbeats. Build leaf-to-root with one worker, then profile the exact declaration if Assembly stalls.

# Final go/no-go checklist

Before considering the N18 port complete, require all of the following:

- [ ] staging and working Lean versions are intentionally aligned or the port is tested against the new version;
- [ ] staging and working mathlib commits are known;
- [ ] `lake-manifest.json` matches the intended dependency pins;
- [ ] `scratch.KeystoneEDS` has an exact reproducible source dependency;
- [ ] no clean build depends on a pre-existing scratch `.olean`;
- [ ] the six relevant modules form an acyclic one-way import graph;
- [ ] Assembly imports low-level dependencies directly;
- [ ] the four ported files build individually from a clean state;
- [ ] `CyclicExclusion18` builds before `CyclicOrderAssembly`;
- [ ] the full `FLT` target builds from a clean state;
- [ ] CI-equivalent tests pass;
- [ ] `#print axioms` for the final N18 theorem contains no custom N18 axiom;
- [ ] `maxHeartbeats 0` is either justified by profiling or localized to known declarations.

If the current build fails, fix the **first error in the first failing leaf module**. In a 4600-line port, later errors are very often cascades from one missing import, changed instance, or mismatched toolchain near the bottom of the dependency graph.
