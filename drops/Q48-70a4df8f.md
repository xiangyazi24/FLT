```lean

```

It contains a constant whose environment name is, in the intended setup,

```lean

```

Inside

```lean

```

```lean

```

by trying namespace prefixes, schematically including

```text

MazurProof.RationalPointsN18Descent.normReal
RationalPointsN18Descent.normReal
```

and any applicable namespace aliases/opened namespaces. If the only matching declaration is

```lean

```

then that is the constant inserted into the theorem type.

Similarly, inside


the source spelling

```lean

```

resolves to the same root declaration, assuming there is no closer shadowing declaration with a duplicated `MazurProof` prefix.

Thus the two source spellings are not two definitions merely because one is shorter. After elaboration they normally contain the identical `ConstantInfo` name.

## Absolute qualification

A multi-component name such as

```lean
MazurProof.RationalPointsN18Descent.normReal
```

is strongly suggestive but is not syntactically root-absolute. The fully shadow-proof spelling is

```lean

```

Using `_root_.` in the shared descent predicate is worthwhile if you expect more staging copies or nested namespaces to be added later.

# 2. Successful `exact` is already the strongest practical type check

The expression

```lean
N18GoodModelAssembly.no_five_descent_solution
  (CyclicExclusion18.order18_to_five_descent E h18)
```

is a function application. To elaborate it, Lean must unify

```text
conclusion type of order18_to_five_descent E h18
```

with

```text
domain type of N18GoodModelAssembly.no_five_descent_solution.
```

For this direct application, Lean accepts equality up to definitional reduction. It does not silently prove an arbitrary logical equivalence between two existential propositions, reorder conjunctions, or invoke `propext` to coerce one proposition into another.

Therefore:

```text
If the displayed theorem compiles, there is no remaining type-mismatch risk at that call site.
```

If the propositions were merely mathematically equivalent but not definitionally equal—for example, one used a differently associated conjunction, a copied `normReal` definition, a different integer type, or reordered existential binders—the application would fail and require an explicit conversion such as `simpa [...]`, `change`, or a bridge theorem.

A minimal standalone compile-time guard is exactly the same application:


If this elaborates in an audit file importing the actual production modules, the producer and consumer types are compatible.

# 5. How `sorry` dependencies work

A declaration proved by `sorry` contains a dependency on Lean's `sorryAx`. Dependency tracking is declaration-level and transitive; it is not module-level.

Consequently:

```text
importing CyclicExclusion18
```

does **not** by itself add `sorryAx` to every theorem in the importing module.

The old staging theorem

```lean
MazurProof.CyclicExclusion18.no_five_descent_solution
```

will itself report `sorryAx`. A theorem that calls it will report `sorryAx`. A theorem that never references it, directly or through another declaration, will not report that particular dependency.

Your new proof term references these two constants:

```lean
MazurProof.CyclicExclusion18.order18_to_five_descent
MazurProof.N18GoodModelAssembly.no_five_descent_solution
```

It does not reference

```lean
MazurProof.CyclicExclusion18.no_five_descent_solution.
```

Therefore the unused staging `sorry` does not contaminate the new `no_order_18`.

Proof irrelevance and runtime dead-code elimination are not relevant here. If the old theorem were referenced anywhere in the proof term, `#print axioms` would see it even if the proposition were proof-irrelevant. The reason your construction is clean is that the old constant is absent from the dependency graph.

# 6. Conditions for the final assembled theorem to be clean

`#print axioms mazur_cyclic_order_bound_assembled` will be free of this `sorryAx` provided all of the following hold:

1. `CyclicExclusion18.order18_to_five_descent` is itself sorry-free transitively.
2. `N18GoodModelAssembly.no_five_descent_solution` is itself sorry-free transitively.
3. `CyclicOrderAssembly.no_order_18` is the theorem actually installed in the order-18 field or branch of the final assembly.
4. No other theorem used by `mazur_cyclic_order_bound_assembled` references `CyclicExclusion18.no_five_descent_solution`.
5. The build is using the intended modules and fresh `.olean` files.

The third point is an easy place for an accidental regression. For example, this is safe:

```lean
no18 := MazurProof.CyclicOrderAssembly.no_order_18
```

whereas this would reintroduce the staging axiom:

```lean
no18 := MazurProof.CyclicExclusion18.no_order_18
```

if that old theorem calls the sorry-backed exclusion.

Likewise, an `inferInstance` or package constructor may hide the selected theorem. `#print axioms` on the final declaration is the authoritative check.

# 8. Build-policy distinction

There are two different notions of cleanliness:

1. **Logical dependency cleanliness:** `#print axioms` for the final theorem does not contain `sorryAx`.
2. **Repository-wide source cleanliness:** no imported source file contains any `sorry` at all.

Your construction achieves the first, assuming the dependency audit above passes. It does not remove the literal `sorry` from `CyclicExclusion18.lean`.

A CI policy that greps all source files for `sorry`, recompiles every file with warnings treated as errors, or uses a repository-wide declaration checker can still reject the tree. That is a policy issue, not contamination of the final theorem's proof term.

If repository-wide cleanliness is eventually required, replace the old theorem with a deprecated forwarding theorem after the import graph permits it, move it to a legacy module excluded from the main build, or delete it. Do not make it forward to `N18GoodModelAssembly` while that would recreate the original cycle.
